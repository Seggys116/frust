# How fRust works

fRust builds a toolchain from a pinned upstream Rust source line (`support/upstream.lock`: Rust 1.100.0, commit `0ef1bc386`, LLVM 23.1.5). `support/apply-patches.sh` applies the Cargo patches in `support/patches/`, `support/apply-rustc-patches.sh` applies the compiler patches in `support/patches/rustc/`, and `support/package-toolchain.sh` assembles the package. Rejected compiler candidates are kept in `support/patches/rustc/dropped/` and are not applied. The compiler series changes as candidates are kept or dropped, so read that directory for the current set.

In the default package, the compiler, standard library and rustdoc match an unpatched stage-2 build byte for byte, and Cargo is patched. Compiler candidates are packaged separately. The toolchain is intended to support the same commands, editions, crates, build scripts and procedural macros as the matched upstream release. `qualification/COMPAT.md` records what has been run, on Linux x86-64 only. Use a matched toolchain for Rust compiler-specific artifacts such as crate metadata and compiled procedural macros. [Rust compiler metadata](https://rustc-dev-guide.rust-lang.org/backend/libs-and-metadata.html)

## What the toolchain contains

An archive is a complete toolchain, laid out like an official one, and it is assembled from two sources.

Built from the pinned sources in this repository's build: `cargo` (patched, also installed as `fcargo` and `frust`), `rustc` (installed as `frustc` as well), `rustdoc` (`frustdoc`), `cargo-clippy` and `clippy-driver` (`fclippy`), `rustfmt` and `cargo-fmt` (`frustfmt`), `rust-analyzer` with its proc-macro server (`libexec/rust-analyzer-proc-macro-srv`), and the standard library of the host. Clippy, rustfmt and rust-analyzer are built here because they link the compiler's internal crates (`rustc_private`) and have to match the compiler they run with. On Linux x86-64 clippy is built with its stored PGO profile ([build assets](build-assets.md)).

Taken from the official Rust 1.100.0 packages: the standard library of every other target (`rust-std`), the `rust-docs` HTML documentation and the `rust-src` library sources (`lib/rustlib/src/rust`, which rust-analyzer needs to expand standard library macros). They are listed with their sha-256 and url in `support/official-components.lock`, fetched by `support/fetch-official-components.sh`, which refuses anything that does not match the lock, and merged into the archive by the packaging step.

Why that is sound. The fRust compiler and standard library are built from the same commit as the official release (`0ef1bc386`), and `rustc -vV` prints the same release, commit hash, commit date and LLVM version as official Rust 1.100.0. The compiler therefore reads the same crate metadata and uses the same standard library interface as the official one. A standard library built by the official release process for another target loads into fRust's sysroot unchanged, and `rustc` checks that identity itself when it opens a library, so a package that did not match would be rejected with a compile error rather than miscompiled. The check was made by compiling a `wasm32-unknown-unknown` cdylib against an official `rust-std` placed next to the fRust host standard library. The documentation and the library sources are text. rust-analyzer is not taken from the official release: it links the official `librustc_driver`, which an fRust tree does not have, so it is built here.

Where this stops. The argument holds while the compiler and standard library keep the official release's identity and interface. A compiler or library change that altered crate metadata or the library's ABI could not reuse the official target libraries and would need its own. `support/toolchain-suite.sh` checks the release and commit hash that `rustc -vV` reports against `support/upstream.lock`, and it builds a library for every bundled target and links where the host can, so an archive whose compiler no longer fits its libraries does not pass.

Targets that are not in the archive come from the same place. `frust-install target add` and `frust-install component add` read the official channel manifest for this release, download the package and check its sha-256 from the manifest before unpacking it into the installed toolchain. The installer records what was added and installs it again after an update ([configuration](configuration.md#targets-and-components)).

## Tools

- `fcargo` (also `frust`, and `fclippy` for `fcargo clippy`) runs the packaged Cargo. It sets `RUSTC` to the sibling `frustc` (`rustc` for clippy) when `RUSTC` is unset, turns on the patched Cargo's central target default, and on a terminal draws build progress. Plain, dumb-terminal, quiet and explicit JSON invocations hand over to Cargo directly. In the packaged toolchain `fcargo` is itself the patched Cargo (a hard link of `cargo`) and the launcher is `fcargo-ui`. See [Cargo startup](#cargo-startup) and [configuration](configuration.md).
- `frust-install` (also installed as `frustup`) takes `install`, `update`, `upgrade`, `stage`, `rollback`, `uninstall`, `target` and `component`. With no command it installs the latest release. `install` and `update` download the archive, its sha-256 file and a one-line id file for this host from the GitHub release (`--version` picks a release, `FRUST_RELEASE_BASE` points at a mirror), skip the download when the id file matches the active version, and install the result. `--archive` and `--checksum` install a local archive instead, and `stage` only unpacks one. The archive's sha-256 is checked against the checksum file before extracting with `tar`. The install requires `bin/rustc`, `bin/cargo`, `bin/rustdoc` and a `manifest.json` id, and switches the `current` symlink only after the tree is complete. `--prefix` defaults to `$FRUST_PREFIX`, then `$XDG_DATA_HOME/frust` or `~/.local/share/frust` (macOS: `~/Library/Application Support/fRust`). Downloads use `curl` or `wget` over https only. The release workflow builds toolchains for `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin` and `x86_64-apple-darwin`, so any other host gets an error naming the missing target. The release validation and Benchmark CI run on Linux x86-64 and both macOS architectures.
- `frust-gates` recomputes the frozen Linux budgets from a file of raw paired samples and exits non-zero when any gate does not pass.

## Cargo startup

Two Cargo patches remove fixed cost from every invocation.

- `0006-frust-lazy-libgit2.patch`: stock Cargo initialized libgit2 at startup, which loads the system CA bundle for TLS. The patch applies libgit2's owner-validation setting and initializes libgit2 on the first git use instead (`ensure_git_init`, called before each libgit2 repository, config or transport entry point). A build that never touches git skips the initialization. Git dependencies, `cargo new`, `cargo fix` and proxy detection through git config behave as before, and the proxy check now tries Cargo's own setting and the proxy environment variables before reading git's config.
- `0008-frust-direct-entry.patch`: on Linux and macOS, when the executable is named `fcargo`, `frust` or `fclippy` (hard links of `cargo`), Cargo itself performs the work `fcargo` used to do before starting Cargo: it sets `FRUST_INVOCATION`, `CARGO`, `RUSTC` and puts the toolchain's `bin` first on `PATH`. This saves one process launch for plain non-terminal invocations. `frust` is the same as `fcargo`; `fclippy` is `fcargo clippy`, with the subcommand inserted (clippy runs use the sibling `rustc` instead of `frustc`, because clippy-driver only accepts a compiler path whose stem is `rustc`). `frust where` and `fcargo where` print the central target directory of the current workspace and exit. Interactive terminals, static progress, an explicit `FRUST_CARGO` and a `+toolchain` argument execute `fcargo-ui` instead, because they need the launcher. See [configuration](configuration.md#direct-entry) for the exact conditions.

## Unit artifact cache

`0007-frust-unit-cache.patch` adds a store of finished compiler outputs inside Cargo, consulted just before Cargo would start rustc. It is on by default under `fcargo` and covers units whose source cannot change between builds, so a clean rebuild, or a new target directory for the same dependencies, can restore outputs instead of compiling. The store is `units/v1` under the artifact cache root ([configuration](configuration.md#unit-artifact-cache)).

**What is eligible.** Library and proc-macro units of registry, git and directory-source packages, built or checked. Path and workspace members, binaries, tests, benchmarks, examples, build script compiles and documentation compile normally. `FRUST_UNIT_CACHE_DEBUG=1` reports why a dependency was skipped, including incremental compilation, rustc wrappers, `-Zbuild-std`, artifact dependencies, custom split-debug output options and missing vendored-source checksums.

**Unpacked debug info.** The default macOS dev profile stores debugger data in separate codegen objects. The cache restores those objects with the library and preserves their modification times for Mach-O debug maps. Mach-O rlibs can be restored to a different target directory. Mach-O dylibs and ELF outputs with unpacked debug info are keyed by their original output directory because their debug data can refer to it. On a cache filesystem without reflinks, an object that exactly matches a member of the cached rlib is stored as a verified byte range. On clone-capable filesystems, separate blobs preserve the ability to reflink each object. Metadata-only checks have no debug objects. A packed macOS `.dSYM` bundle still takes the normal compile path.

**Key.** A BLAKE3 hash over the exact compiler and sysroot identity (`rustc -vV`, the sysroot path, the name, size and modification time of the sysroot library files, and the toolchain id file when present); the package identity (id, source URL with the git revision, registry checksum, and the full text of a vendored directory source's checksum file); the complete compiler argument list, with target-directory paths replaced by a token and each `--extern` file replaced by its content hash; the environment Cargo sets plus a short list of inherited variables that affect output; the content of native static archives and link-arg files that can reach the output; and the working directory, only when debuginfo is enabled. Timestamps of sources are never part of the key.

**Second check.** After a compile, the store records the environment variables and out-of-package files that rustc read, as listed in its dep-info. A lookup re-verifies them. An output tied to the build directory, through a file or an environment value under it, only hits in the same build directory.

**Restore and fallbacks.** Each output is staged next to its destination. An output restored by copy is checked by size and BLAKE3 as it is written. For a reflink, the clone is checked before publication. Cargo verifies dep-info and messages when it reads them, and renames the staged files into place only after verification succeeds. A corrupt entry is removed when the store is writable. A cache miss, contended entry or failed restore falls back to the compiler. A read-only store can still serve verified hits. Writers take a per-entry lock and publish the manifest last. A unit that printed diagnostics is not stored. The `unused_extern` reports are stored and replayed on a hit.

New entries keep dep-info and message text up to 1 KiB in the manifest. Inline text and separate blobs both carry length and BLAKE3 checks. Existing entries with separate blobs still restore.

**Build script runs.** The same store holds the output of build script runs of registry and git packages that took at least `FRUST_UNIT_CACHE_SCRIPT_MIN_MS` (3000 ms by default): the script's `stdout`, `stderr` and its whole OUT_DIR tree. The key covers the complete environment (minus a few variables that only vary between invocations, make's job-count flags and the `FRUST_UNIT_CACHE*` controls), the script binary's content, the package identity, the identity of the C toolchain and build tools found on `PATH` and in `CC`, `CXX`, `AR` style variables (including cross compiler names), the modification times of system header and library directories, and the outputs of upstream build scripts. The environment includes the OUT_DIR path, so an entry is bound to the exact build directory: it serves clean rebuilds at the same target path, not other projects. A run is stored only when it started from an empty OUT_DIR, changed nothing in the directories around OUT_DIR other than Cargo's own files, printed no `cargo:warning` or error lines, and left a tree under 2 GiB made of files, directories and relative symlinks that stay inside the tree. Cheap probing scripts fall under the threshold on purpose, because their results depend on system state. A hit is also refused when a `rerun-if-changed` file outside the package changed, or when a library search path it names inside the build directory no longer exists.

**Limits.**
- A proc-macro or build script that reads an environment variable or file that rustc and Cargo do not report depends on that input as it does under plain Cargo. The cache cannot see it.
- The build script key tracks the listed tools and system directory modification times. A change to another tool or library, or a change that leaves those timestamps alone, is not detected.
- The check for build script writes outside OUT_DIR looks at the directories around it, not at the whole disk.
- A first build with an empty store also writes entries. `docs/benchmarks.md` points to where the cost is recorded.

**Evidence.** `qualification/prove-unit-cache.py` covers byte-identical restored and fresh outputs, feature, flag, environment and toolchain misses, proc macros, concurrent builds, corrupted entries, a read-only store, vendored source edits, memory-mapped source edits and build scripts. The release suite uses the default native profiles and compares restored macOS debug objects against an uncached compile.

## Incremental builds

Incremental compilation is stock rustc's. A source edit invalidates compiler queries through recorded dependencies, and unaffected analysis and code generation are reused when their inputs are still valid. fRust does not change that. A one-file change can still affect many items through types, generics, macros, constants or inlining. [Rust compiler incremental compilation](https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation-in-detail.html)

The Cargo patch `0002-frustc-content-fingerprint.patch` changes Cargo's freshness check only when its compiler path is named `frustc`. After each such compile, Cargo stores a BLAKE3 checksum and length for dep-info inputs that rustc did not already checksum, and the next build compares them. A same-size edit whose timestamp was restored is therefore rebuilt. A file saved while the compiler ran gets no checksum, so the next build treats it as dirty. With `rustc` Cargo keeps its timestamp check.

On Unix, Cargo creates or truncates its invocation marker to record a filesystem modification time. An empty marker carries the same timestamp and uses no file data block.

## Release code generation and linking

The requested optimization profile governs code generation. Any reuse before the whole-program step comes from stock rustc's incremental compilation, and fat LTO then optimizes the merged module. A pre-optimization cache that tried to add reuse before that step failed the paired Linux gate and was dropped, so fRust does not add reuse there. A changed whole-program input still runs the LTO pipeline.

The one reuse change kept after fat-LTO optimization is an object cache in `frustc`. When the optimized module is emitted as a single object, `frustc` hashes it and looks for an object with the same hash in a `frust-codegen-cache/` directory next to the output object. A hit copies that object and skips machine-code emission. A miss emits normally and stores the object. The LTO optimization pipeline runs either way. The hash covers function bodies, global initializers, linkage, attributes, the data layout, the target triple and module flags, ignores symbol order, and does not include debug-info nodes. A module with debug info, or a build that writes split DWARF, is not cached. The file name is the hash plus the optimization level and the no-builtins setting. A hit needs an edit that leaves the optimized module unchanged. The recorded single samples show a speedup only on the ripgrep leaf edit and none on the syn and regex library edits or the fd holdout (`qualification/CANDIDATE.md`).

A second piece passes `-z pack-relative-relocs` to the GNU linker at opt-level 2 or 3 for GNU-style ELF links that are not `crt-static` and not WebAssembly. The output carries a `GLIBC_ABI_DT_RELR` version requirement, so it can require glibc 2.36 and a linker that supports packed relative relocations.

Both pieces apply only when the executable is named `frustc`, and the current patch enables them only with `FRUST_EXPERIMENTAL_CODEGEN_CACHE=1` and `FRUST_EXPERIMENTAL_RELR=1`. Otherwise code generation and linking use the upstream behavior. Give every experimental configuration its own clean target directory. The cache key is the module hash, the optimization level and the no-builtins setting. Whether that covers every setting that affects machine-code emission has not been verified. `qualification/CANDIDATE.md` does not state which values of these switches the recorded measurements used. Native linking has been measured on Linux x86-64 only, and explicit linker selection is not changed. [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html) · [LLVM LTO](https://llvm.org/docs/LinkTimeOptimization.html)
